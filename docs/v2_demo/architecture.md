# V2 Demo Architecture

## 1. Goal

V2 adds a portfolio-ready web demo on top of the v1 PyTorch pipeline. The demo
is an ML pipeline explorer, not a replacement for the v1 training and
evaluation scripts.

The frontend is a Vite + React + TypeScript single-page app ported from the
Claude Design handoff. The MVP is fully static — the frontend reads
pre-generated JSON and PNG artifacts with no Python backend required. A later
milestone can add a FastAPI backend for live checkpoint inference.

Canonical design reference: `docs/v2_demo/frontend-design-handoff.md`

## 2. High-level flow

```text
Curated sample manifest
        |
        v
Saved v1 artifacts
  ultrasound, target mask, probability map, prediction mask, metrics
        |
        v
Vite + React static frontend
        |
        +--> Data and target-mask view
        +--> CNN prediction/probability view
        +--> Threshold and cleanup view
        +--> Ellipse and HC measurement view
        +--> Experiment dashboard
```

Future live inference adds:

```text
Selected curated image
        |
        v
FastAPI checkpoint inference adapter
        |
        v
JSON compatible with the same React Sample interface
```

Arbitrary upload is a later, explicitly approved extension. The first live mode
is curated-sample-only so it can reuse known spacing, target metadata, and demo
copy without turning the app into a public medical-image upload tool.

## 3. App modes

### Saved-output mode

Saved-output mode is the v2 MVP.

Responsibilities:

- load a small manifest of curated samples,
- read exported demo artifacts plus existing v1 result tables,
- display each pipeline stage without loading a model checkpoint,
- compute lightweight interactive geometry variants when needed,
- show v1 result tables and figures.

This mode should run without raw HC18 data or checkpoints if the curated
artifacts are present. Existing files under `outputs/runs/<run_id>/` can seed
the export, but the app should read the stable demo bundle instead of reaching
back into raw HC18 paths at runtime.

### Live-inference mode

Live-inference mode is a later extension.

Responsibilities:

- load a PyTorch checkpoint,
- preprocess selected curated images,
- run model inference,
- produce the same stage objects as saved-output mode,
- return live-generated image assets as URLs or data URLs through component
  asset overrides,
- use the existing deterministic geometry utilities.

This mode may require a checkpoint and either the local HC18 sample source or an
approved curated live bundle. It must keep the safety disclaimer visible and
must not become a dependency of saved-output mode.

Implementation plan:
See `docs/v2_demo/live-inference-plan.md`. The first implementation should use
`demo_live/` as the FastAPI companion server and keep `frontend/public/samples/`
manifest loading unchanged for static replay.

## 4. Demo file layout

The frontend is a React app. The Python `demo/` directory is no longer used.

```text
frontend/                         ← Vite + React + TypeScript app
  src/
    components/                   ← one folder per design component
    data/                         ← stages.ts, metric-copy.ts, samples.ts
    types/sample.ts               ← TypeScript interfaces (Section 5)
    styles.css                    ← design tokens (from design handoff styles.css)
    App.tsx
  public/
    samples/
      manifest.json               ← generated by V2.S2 export script
      <sample_id>/
        ultrasound.png
        target.png                ← annotation-derived mask
        pred.png                  ← cleaned binary prediction
        prob.png                  ← raw sigmoid probability map (uint8 grayscale)
  package.json
  vite.config.ts

outputs/demo_samples/             ← generated locally by V2.S2, copied to frontend/public/samples/
  manifest.json
  <sample_id>/
    ultrasound.png
    target.png
    pred.png
    prob.png
    metadata.json                 ← per-sample numeric fields (merged into manifest.json)
```

Dev/build commands:
```bash
cd frontend && npm install && npm run dev    # dev server → localhost:5173
cd frontend && npm run build                 # production → frontend/dist/
```

## 5. App-facing data contract

The frontend TypeScript `Sample` interface is the authoritative data contract.
The Python `DemoSample` dataclass is no longer used. See
`docs/v2_demo/frontend-design-handoff.md` Section 6 for the full interface.

Summary of required fields per sample in `manifest.json`:

```typescript
interface Sample {
  id: string;                  // e.g. "296_HC"
  label: string;               // human title
  cat: 'strong' | 'typical' | 'failure';
  split: string;               // "test"
  summary: string;             // 1-line description
  metrics: {
    dice: number;
    iou: number;
    hd95_mm: number;
    hcErr: number;             // abs_hc_error_mm
    predHC: number;            // pred_hc_mm
    targetHC: number;          // target_hc_mm
  };
  predEllipse: {               // from predictions.csv ellipse columns
    cx: number; cy: number;
    rx: number; ry: number;
    rot: number;               // RADIANS (convert from ellipse_angle_deg)
  };
  contourHC: number;           // mm — computed by export script from cleaned mask
  confidence: number;          // mean prob inside predicted mask — from prob.png
  spacingXMm: number;          // spacing_x_mm from predictions.csv
  spacingYMm: number;          // spacing_y_mm from predictions.csv
  resolution: { w: number; h: number };  // px dimensions of exported images
  notes?: string;
}
```

The frontend TypeScript interface is the authoritative contract. See Section 5 above
and `docs/v2_demo/frontend-design-handoff.md` Section 6.

## 6. Manifest schema

The manifest is at `outputs/demo_samples/manifest.json` (generated by V2.S2)
and copied to `frontend/public/samples/manifest.json` before the frontend builds.
Image paths are not stored in the manifest — the frontend derives them as
`/samples/<id>/<file>.png` using each sample's `id`.

```json
{
  "schema_version": 2,
  "created_from_run_id": "attention_unet_local_baseline",
  "created_from_split": "test",
  "safety_text": "Educational demo only. Not for clinical use.",
  "samples": [
    {
      "id": "296_HC",
      "label": "Near-perfect HC",
      "cat": "strong",
      "split": "test",
      "summary": "Excellent overlap and near-perfect head-circumference measurement.",
      "metrics": {
        "dice": 0.9907,
        "iou": 0.9816,
        "hd95_mm": 0.70,
        "hcErr": 0.03,
        "predHC": 191.44,
        "targetHC": 191.47
      },
      "predEllipse": {
        "cx": 205.4, "cy": 114.2,
        "rx": 83.1, "ry": 66.7,
        "rot": 2.872
      },
      "contourHC": 192.20,
      "confidence": 0.97,
      "spacingXMm": 0.1367,
      "spacingYMm": 0.1384,
      "resolution": { "w": 384, "h": 256 },
      "notes": "Best success-path example."
    }
  ]
}
```

Notes on generation:
- `predEllipse.rot` is `ellipse_angle_deg * pi / 180` (convert from degrees)
- `contourHC` is computed at export time from cleaned mask using `src/utils/geometry.py`
- `confidence` is `mean(prob_map[cleaned_mask == 1])`, requires `prob.png`
- All `metrics` values come from real v1 CSVs, not placeholder values
- `cat` uses `'failure'` not `'edge'`

## 7. Core components

The frontend components are defined in the design handoff. See
`docs/v2_demo/frontend-design-handoff.md` for the full component inventory and
porting instructions. Summary:

### SampleGallery
Card gallery with category filter (All / Strong / Typical / Failure).
Active card gets cyan glow border. Clicking a card sets `activeId` and
auto-advances the pipeline stepper.

### PipelineStepper + StageDetail
Six-stage horizontal stepper with connecting progress line. Each stage shows
an image composite (ultrasound + mask/prob overlay via CSS blend modes + SVG
ellipse). Stage detail panel shows plain-English explanation and per-stage callout.

### ThresholdViewer (hero interaction)
Canvas-based real-time re-thresholding of `prob.png` pixel data. Must preserve
the soft-edge blend and histogram strip from the design exactly.

### CNN prediction visualization

Saved-output mode must show the exported `prob.png` and `pred.png` artifacts.
If probability-map export fails for a sample, validation should fail rather than
letting the app pretend to show probabilities.

Live-inference mode can add probability heatmaps directly from model logits.

### Geometry visualization

This view uses existing geometry utilities where possible:

- thresholded mask,
- largest connected component cleanup,
- contour measurement,
- ellipse fit,
- HC in millimeters.

It should always show the contour-vs-ellipse comparison when both measurements
are available, because this was one of the strongest v1 findings. If contour HC
cannot be computed for a sample, the UI should mark that value unavailable
rather than hiding the ellipse result.

### Experiment dashboard

The dashboard reads v1 report tables and figures, especially:

- main test results,
- Attention U-Net ablations,
- post-processing ablation,
- HC MAE figures,
- training loss and validation loss curves from `outputs/runs/*/metrics.csv`.

The dashboard should emphasize that v1 used a local reduced-resource setup.

## 8. Artifact export step

Before building the React app, revise the export script so it creates the
saved-output demo bundle required by the design:

```text
scripts/export_demo_artifacts.py
scripts/validate_demo_manifest.py
```

This export step requires local HC18 raw data at `data/raw/HC18/training_set/`
because the original image and annotation-derived target mask are not already
part of the raw-data-free demo bundle. After export, the React saved-output mode
must run without `data/raw/HC18/` or a model checkpoint.

The exporter should:

1. choose a fixed set of internal-test samples from v1 prediction/evaluation
   artifacts, using `docs/v2_demo/curated-samples.json` or explicit
   `--sample-id` arguments,
2. copy or render `ultrasound.png`, `target.png`, and `pred.png` into
   `outputs/demo_samples/<sample_id>/`,
3. run local checkpoint inference once to export `prob.png` as the raw sigmoid
   probability map,
4. compute cleaned-mask contour HC in millimeters and store it as `contourHC`
   in the manifest,
5. compute confidence, prediction ellipse, pixel spacing, and image resolution
   fields required by the TypeScript `Sample` contract,
6. write per-sample `metadata.json` for traceability,
7. write `outputs/demo_samples/manifest.json`,
8. avoid committing raw HC18 files, generated medical-image bundles, or
   checkpoints unless the user explicitly
   approves a separate artifact policy.

The validator should confirm required files exist, required fields have numeric
types, `contourHC` is non-null when contour measurement succeeds, `prob.png` is
present for every sample, and the manifest includes both strong and failure
examples.

## 9. Distribution policy

The first implementation should treat `outputs/demo_samples/` as a generated
local artifact bundle. Do not commit raw HC18 images, checkpoints, or generated
medical-image demo bundles without explicit user approval.

The current `.gitignore` ignores `outputs/*`, including `outputs/demo_samples/`,
which is the correct default for local generated artifacts. If portfolio
screenshots or GIFs are approved later, place them in a non-ignored documentation
path such as `docs/v2_demo/screenshots/` rather than under `outputs/`.

For portfolio polish, prefer one of these paths after the local MVP works:

- publish a small `demo-artifacts-v1.zip` as a GitHub Release asset and document
  a download command,
- commit only non-sensitive screenshots/GIFs for README presentation,
- keep a local-generation command for reviewers who already have HC18.

This keeps the saved-output app stable while leaving the artifact-distribution
choice explicit.

Public hosting fallback:
The committed app includes non-medical preview assets under
`frontend/public/demo-samples/`. At runtime, the frontend first tries
`/samples/manifest.json` for the real local saved-output bundle. If that file
is absent on a public static host, it falls back to
`/demo-samples/manifest.json` so the deployed app remains reviewable without
publishing HC18-derived sample images.

## 10. Boundaries

- The demo must not mutate raw data or split files.
- The demo must not train models.
- The demo must not silently regenerate v1 experiments.
- The demo should not require internet access.
- The demo is educational and not for clinical use.
